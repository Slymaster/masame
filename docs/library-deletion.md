# Local library deletion

Each library row has separate open and delete controls. Deletion asks for confirmation, removes the local SGF and its analysis sidecars, and clears `current.json` only when it points to that game. An OGS copy is local data: no OGS deletion request is made. Importing the server game explicitly creates a new local copy.

The UI keeps the row until the native command succeeds. A failure displays an error while keeping the row available for retry. Deleting the displayed game returns to an empty board with no AI opponent. Existing exercises, repetition schedules, rank history and earned rewards are separate stores and are retained. Statistics derived from library entries reflect the remaining entries.

Before the command is queued, pending autosaves and background reviews for the id are invalidated. Work in flight carries a generation guard, including foreground review and tsumego mining. A deleted board cannot save itself again after reimport. Restored review queues are reconciled against the library before running. If deletion fails, autosaving of the displayed game is rearmed.

Deleted OGS ids also remain in the native `games/deleted.json` opt-out list across restarts. Before automatically keeping or reviewing an OGS game, the app awaits `library_admit`; a rejected or failed read cannot enqueue analysis or write SGFs/sidecars. This covers the recent `gameEnded` notifications OGS replays on reconnect. Only an explicit import clears that id. Admission responses and their generation changes use the write queue, so an old refusal cannot reblock a successful explicit import. A rejected Game remains inactive after a later import, and a failed native write restores the previous UI entry.

The native store uses a `.delete` journal under its mutex. It backs up index/current/OGS opt-out metadata, stages game files by rename, then commits metadata and a marker. A failed opt-out write rolls the whole deletion back. Before commit, an interrupted operation rolls back on the next store access; after commit it finishes cleanup. A cleanup failure after commit leaves the journal for retry without restoring the deleted entry. This protects against process termination and ordinary filesystem errors; it is not a guarantee against storage hardware failure. Corrupt or unreadable opt-out metadata fails closed and needs its storage problem resolved before further OGS imports; it is never silently discarded.

## Verification

- `pnpm test` and `pnpm build`.
- `cargo test --locked --manifest-path tests/library-native/Cargo.toml` runs the production Rust store directly, without a GUI or engine installation. The dedicated workflow runs it on Linux, Windows and macOS. Tests cover cascade, current pointer matching, retry after an I/O error, interruption before/after commit including opt-outs, neighboring ids and unrelated learning data. TypeScript tests reset the module's RAM while retaining native storage, replay a real parsed notification aged 60 seconds, verify zero automatic writes/sidecars/jobs, then explicitly import one copy. They also cover admission failure, delayed refusal versus explicit import, and rejected native writes.
- Browser fixture: run `pnpm dev`, then open `/tests/fixtures/library-delete.html`. All native calls use disposable in-memory data. Cancel the confirmation and verify the row remains. Close the sheet, enable the simulated disk error, reopen and confirm deletion: the error and row must remain. Disable the error and retry: the row disappears. The fixture's learning counters are illustrative, not a test of the learning stores or the App board-reset path.
- Native device suspension and full application board reset require the packaged application. The portable tests do not claim an end-to-end native UI test.
